## 1. 内容主线与边界

核心访客为 Shopify 商家 / 服务商及多品牌、多站点团队。首页先以 Shopify 的 SEO/GEO 与站点健康问题牵引，再解释平台扩展能力；首发客户的规模、行业与采购角色仍需确认。

统一叙事：**业务问题 → 发现与分析 → 可审阅建议 → 授权执行 → 结果验证 → 持续运营**。

内容必须回答四个问题：解决谁的什么问题、接入需要什么、能够交付什么、哪些操作仍需人工决定。接入后 24 小时、首周或任何效果指标，均须有真实依据后才能写成承诺。

主 CTA 使用 Book a Demo，次 CTA 引导产品说明与场景页。以下 H1 均为中文工作方向；英文 Hero 保留源文档工作稿，最终语言需统一确认。

## 2. P01 首页 Home

**目标**：让访客在 30 秒内理解产品类别、首发价值与下一步。  
**H1 工作稿**：AI-powered operations for modern commerce.

| 顺序 | 模块 | 内容要点 | 素材 / 证据 | 下一步 |
| --- | --- | --- | --- | --- |
| 01 | Hero | 产品信息、内容、搜索表现与站点健康协同；补一句已可兑现的首发价值 | 真实界面，或明确标注“概念示意”的画面 | Book a Demo → `/contact`；Explore the Platform → `/product` |
| 02 | 业务问题 | SEO 异常、产品描述冲突、站点故障和 AI 搜索可读性分散在多个工具 | 来自目标客户的实际问题描述 | `/product` |
| 03 | 平台总览 | 连接渠道 → 监测分析 → 问题中心 → 审阅建议 → 执行与验证 | 与实际产品一致的流程图 | `/platform/how-it-works` |
| 04 | SEO & GEO | 检查范围、问题优先级、建议与复检；突出首发入口 | 已核实检查清单和问题样例 | `/product/seo-geo` |
| 05 | Product Knowledge | 产品事实、属性、关系和跨渠道描述一致性 | 一组产品事实与渠道差异示例 | `/product#product-knowledge` |
| 06 | SiteOps | 从一条站点异常说明发现、影响定位与恢复验证 | 有来源的异常及复检记录 | `/product#siteops` |

| 08 | Shopify 场景 | 接入后得到什么、需要什么权限、下一步如何开始 | 确认后的接入方式与首个交付物 | `/solutions/shopify` |

| 11 | 结尾转化 | Run your sites with more clarity and less manual work. | 简要说明演示包含什么 | `/contact` |

**待核验**：首发价值、产品画面、示例数据、功能状态及每个入口是否可用。没有客户授权与结果数据时，不放客户墙、评价或提升百分比。

## 3. P02 Product Overview

**读者 / 目标**：需要理解平台全貌的运营和技术决策者；回答各项能力如何协作。  
**H1 方向**：连接产品、内容、搜索表现与站点运营。

| 顺序 | 模块 | 需要表达的内容 |
| --- | --- | --- |
| 01 | 使用场景 | 谁在使用、目前的问题为何分散、平台负责哪一段工作 |
| 02 | 四个支柱 | SEO & GEO、Product Knowledge、SiteOps、AI Agents；逐项标注实际状态 |
| 03 | 从问题到行动 | 用同一问题展示分析、建议、审批、执行和复检，避免各模块各说各话 |
| 04 | 渠道与多站点 | Shopify、Strapi 和其他经确认渠道如何共享事实或任务 |
| 05 | 控制与记录 | 操作权限、人工控制、执行记录和失败处理边界 |
| 06 | 演示入口 | 根据访客平台与业务问题预约演示 |

**素材**：能力状态表、平台结构图、一条贯穿案例。  
**内链**：SEO & GEO、How It Works、Integrations、Security；建立 `#product-knowledge` 与 `#siteops` 区块。  
**核验点**：Multi-site Content 首期作为协作语境说明，不额外包装为已交付的第五项核心能力。主 CTA → `/contact`。

## 4. P03 SEO & GEO

**读者 / 目标**：增长负责人、SEO 团队、Shopify 商家和代理商；明确检查范围与可验证结果。  
**H1 方向**：发现搜索与内容问题，把建议推进到复检。

1. **常见问题**：元信息缺失、断链、内容冲突、结构化数据等，以实际支持项为准。
2. **覆盖范围**：按技术 SEO、内容质量、结构化数据、AI 搜索可读性分类，说明输入数据、输出结果和限制。
3. **问题优先级**：展示影响页面、问题说明及处理建议；优先级依据须与产品一致。
4. **建议与批量处理**：对比建议内容、可编辑范围、审批要求及失败反馈；未支持批量写入时不展示一键修复。
5. **结果验证**：用检查结果前后变化说明是否修复，区分技术检查通过与自然流量变化。
6. **相关能力**：连接 Shopify 场景与 Product Knowledge，说明产品事实如何影响内容一致性。
7. **FAQ 与演示**：数据权限、扫描范围、人工工作和报告形式。

**素材**：一份可公开审计报告、问题详情、建议对比、复检记录。  
**主 CTA**：Book a Demo → `/contact`；次入口 → `/solutions/shopify`。  
**核验点**：每一项检测能力均需确认；GEO 不保证 AI 助手收录、引用或排名，不以示意图暗示已获得此类结果。

## 5. P04 Shopify Solution

**读者 / 目标**：Shopify 商家与服务商；说明接入后的首个实际结果与所需投入。  
**H1 方向**：从 Shopify 店铺问题清单开始，推进可审阅的改善。

| 模块 | 内容安排 | 需确认 |
| --- | --- | --- |
| 适用对象 | 哪类店铺、团队和问题最匹配 | 首发客户细分与暂不适用情况 |
| 接入准备 | 安装或连接方式、授权对象、读取与写入范围 | App 状态、权限清单、授权流程 |
| 首次结果 | 扫描范围、问题清单、影响页面与建议 | 可交付内容及真实所需时间 |
| 审阅与处理 | 商家如何查看建议、批准操作、查看结果 | 自动化与人工边界 |
| 复检与持续跟踪 | 同一问题的验证结果及后续监测 | 复检方式、监测频率与支持范围 |
| 采购 FAQ | 接入投入、是否改动主题、试点、支持与退出 | 经产品与商务确认的实际安排 |

**叙事形式**：可使用“接入后的第一周”作为演示结构，步骤和时间均须核实；未核实前只描述接入顺序，不承诺七天内产生特定效果。  
**素材**：接入流程、权限说明、首次报告和复检样例。  
**主 CTA**：Book a Demo → `/contact`；可安装且流程可用后才替换或新增 Install Shopify App。

## 6. P05 Strapi & Multi-site Solution

**读者 / 目标**：多品牌、多站点内容及技术团队；解释如何与现有 Strapi 协作。  
**H1 方向**：让多品牌、多站点内容围绕一致的产品事实协作。

1. **团队问题**：品牌、语言和渠道各自维护内容所造成的差异。
2. **组织结构**：品牌 → 站点 → 语言 / 市场的示意；说明哪些是现有支持、哪些待扩展。
3. **与 Strapi 的关系**：哪些内容继续由现有 CMS 管理，平台负责何种分析、治理或协作。
4. **产品事实流转**：来源 → 事实与属性 → 审核 → 同步或发布 → 差异检查；逐段说明实际支持范围。
5. **多站点治理**：建立 `#multi-site` 区块，说明权限、审批和隔离边界。
6. **实践示例**：选一个可公开的跨站点产品内容差异，展示处理过程。
7. **接入与演示**：前提条件、所需资料、迁移或试点安排（待确认）。

**素材**：已有实践结构图、内容流转图、差异案例与权限说明。  
**主 CTA**：Book a Demo → `/contact`；关联 Integrations、Security。  
**核验点**：现有项目实践不等于多租户 SaaS 已全面交付，不默认承诺自动同步全部渠道或直接复用所有客户环境。

## 7. P06 How It Works

**读者 / 目标**：运营和技术评估者；明确从连接到验证的责任边界。  
**H1 方向**：从连接渠道到验证结果，每一步都有清晰记录。

| 步骤 | 展示内容 | 必须交代的边界 |
| --- | --- | --- |
| 01 连接 | 选择渠道、授予权限、确定对象范围 | 实际支持的接入方式 |
| 02 监测与分析 | 获取数据并识别问题 | 数据来源、覆盖范围、频率 |
| 03 Issue Center | 汇总问题、影响对象和建议 | 优先级依据与负责人机制（如支持） |
| 04 Agent 建议 | 建立 `#agents`，展示建议、拟执行动作与所需权限 | 真实建议或示意的明确标签 |
| 05 审批与执行 | 谁能批准、实际修改了什么 | 自动化边界、失败反馈、可撤销范围 |
| 06 验证与记录 | 复检结果、未解决原因与任务记录 | 什么算成功、何时仍需人工处理 |

**核心内容资产**：全站复用同一条“问题 → 建议 → 审批 → 验证”案例。本页讲完整流程；首页展示摘要；SEO 页解释检查；Shopify 页解释接入上下文。  
**主 CTA**：Book a Demo → `/contact`；关联 Security、Integrations。  
**核验点**：回滚、审计、自动审批等只有实际支持才写为现有功能。

## 8. P07 Integrations

**读者 / 目标**：渠道负责人和技术团队；判断能否接入以及接入后支持什么。  
**H1 方向**：连接正在运营的渠道，清楚了解每项集成的边界。

内容顺序：集成总览 → 按状态展示连接器 → 单项接入范围 → 读写权限 → 接入步骤 / 申请方式 → FAQ → 联系入口。

每张集成卡至少需要：

| 字段 | 内容要求 |
| --- | --- |
| 名称与 Logo | 仅展示真实支持或有明确计划的渠道 |
| 状态 | Available / In development / Planned；内测单独标明 Beta 及准入范围，不能直接归为全面可用 |
| 数据对象 | 实际可读取、分析或写入的数据类型 |
| 能力与限制 | 支持哪些流程，不支持或需要人工处理哪些部分 |
| 权限与前提 | 必要权限、安装条件及版本要求（如有） |
| 行动入口 | 可用连接入口或联系申请；无可用目标时只显示状态 |
| 核验信息 | 内部保留负责人、证据与最后核验日期 |

Shopify 与 Strapi 是源文档的重点渠道，不据此推断它们当前均为 Available。  
**主 CTA**：Discuss your integration → `/contact`。不承诺未确认发布日期。

## 9. P08 Security & Governance

**读者 / 目标**：采购、技术及数据责任人；了解授权、人工控制和实际数据边界。  
**H1 方向**：明确授权范围，让 AI 操作可审阅、可追溯。

| 模块 | 内容问题 | 证据要求 |
| --- | --- | --- |
| 授权与最小权限 | 连接什么、读取什么、何时需要写入 | 实际权限清单与授权方式 |
| 数据边界 | 数据存放、访问和隔离如何处理 | 当前架构和已验证隔离范围 |
| 人工控制 | 哪些建议需审批，谁能决定执行 | 实际权限及审批流程 |
| 操作记录 | 记录什么，如何查看、保留多久 | 日志样例与真实策略 |
| 失败与撤销 | 执行失败怎么处理，哪些动作可回退 | 已支持的机制与限制 |
| 数据使用与退出 | AI 处理涉及什么、断开连接和删除如何申请 | 实际供应商、数据流程与退出政策 |
| 进一步沟通 | 技术问题、采购问题的接收方式 | 有人维护的联系渠道 |

**素材**：经过脱敏的权限、审批和任务记录示例。  
**主 CTA**：Discuss requirements → `/contact`；关联 Privacy。  
**核验点**：不自行增加认证徽章、合规结论、加密规格、数据保留期限、SLA 或“零数据风险”等表述；未知项列内部待确认，不以宣传文案填补。

## 10. P09 Contact / Book a Demo

**目标**：让访客知道演示包含什么，并成功提交可跟进的需求。  
**H1 方向**：聊聊你的店铺与内容运营需求。

内容顺序：演示价值 → 演示可覆盖的问题 → 简洁表单 → 提交反馈 → 备用联系方式。

| 字段建议 | 必填建议 | 用途 |
| --- | --- | --- |
| 联系人姓名 | 是 | 后续称呼与沟通 |
| 联系邮箱 | 是 | 回复申请，不默认加入营销订阅 |
| 公司 / 品牌 | 是 | 了解业务主体 |
| 网站 / 店铺 URL | 否 | 预先理解场景 |
| 使用平台 | 是 | Shopify / Strapi / 多渠道 / 其他，可多选 |
| 主要需求 | 是 | SEO/GEO、站点健康、产品内容、多站点、代理商合作或其他 |
| 补充说明 | 否 | 提供背景、时间和特殊需求 |

字段是本次规划建议，最终根据销售需要与必要的数据收集范围确认。表单旁提供隐私说明入口；如涉及营销订阅，单独设计选择与说明。

**状态文案**：

- 提交中：明确正在提交，避免重复提交。
- 成功：确认申请已收到，并说明下一步；只有跟进时效已确认时才承诺回复时间。
- 校验失败：在对应字段说明问题，并保留输入。
- 提交失败：说明可重试，提供已确认的备用联系渠道。

**跟进规划**：按商家、企业、多站点和代理商需求分流，明确接收人及处理方式。  
**建议追踪**：演示 CTA 点击、表单开始、提交成功和提交失败，记录来源页；具体埋点方案在开发阶段确定，不将邮箱、姓名等表单内容写入分析事件。  
**核验点**：现有联系 API 只是代码基础，必须另行确认字段、后端及接收流程。

## 11. P10 Privacy 与 P11 Terms

| 页面 | 内容准备范围 | 所需输入 |
| --- | --- | --- |
| Privacy | 适用主体、收集信息、用途、第三方处理、保留与删除、联系渠道、生效日期 | 网站与产品实际数据流、表单字段、分析工具、服务提供方及经审核文本 |
| Terms | 适用主体与范围、用户使用要求、服务边界、知识产权、商业条款引用、变更与联系渠道 | 实际服务模式、试点或套餐安排及经审核文本 |

首期提供独立可访问页面，在页脚和相关表单处链接。网站访客政策与平台产品条款是否合并，依据实际服务范围确认。本阶段只列资料要求，不据此认定任何法域义务或生成正式法律文本。

## 14. 页面级 SEO 与语言准备

以下为内容准备项，不是排名承诺。

| 页面组 | 独立主题 | 元信息准备方向 |
| --- | --- | --- |

| Product | 平台能力协作 | 避免与首页重复，仅解释产品如何组成工作流 |

每页准备唯一 H1、页面标题、描述、分享图、图片替代文本与相关内链。正式品牌名确定前不定稿 Title；正式域名及语言结构确定后再配置 canonical、语言 alternate、站点地图和适用的结构化数据。先完成主语言内容确认，再组织翻译；代码现有英文默认值不视为市场语言决策。

## 15. 内容完成与交接标准

每个首发页面交接前应具备：

- 已确认的页面目标、模块顺序、H1、文案和明确 CTA 目标。
- 已收集素材、来源与使用范围；缺口明确登记。
- 所有功能、安全、时效和业务结果声明完成核验。
- 主语言元信息及翻译安排明确，内链只指向本期可用页面或区块。
- 联系表单、演示接收和政策文本有负责人；页面实现后的运行验证另行完成。

建议状态流转：**待资料 → 内容草稿 → 产品 / 业务核验 → 文案确认 → 设计交接**。当前两份规划文档处于“内容草稿”，未进入实现或上线验收。
