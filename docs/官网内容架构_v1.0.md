# AI 原生 Commerce & Content Operations 平台｜宣传官网内容架构 v1.0

日期：2026-09-27  
状态：官网策划草案；产品功能与商业承诺需在上线前核验。

## 1. 定位与叙事

**一句话定位**：连接 Shopify、Strapi 与其他业务渠道，持续发现并协助处理产品信息、内容、SEO/GEO 和站点运营问题的 AI 原生平台。

**英文工作稿**：AI-powered operations for commerce and content.  
**中文工作稿**：让产品、内容、搜索表现与站点健康始终处于掌控之中。

官网面对两类主要访客：Shopify 商家或服务商，希望快速发现并修复店铺问题；多品牌、多站点团队，希望统一产品事实、内容治理和跨渠道运营。SEO/GEO 是首期最清晰的获客入口；Product Knowledge、SiteOps、AI Agents 共同解释平台的长期价值。

页面叙事顺序：**业务问题 → 平台如何发现问题 → 可审阅的建议与执行 → 渠道适配 → 治理与可信度 → 转化**。营销语言应随实际上线范围调整，避免暗示所有展示能力已经可用。

| 顺序 | 模块 | 核心信息与展示 | 行动入口 |

| 02 | 业务问题 | SEO 异常、产品信息不一致、站点故障、AI 搜索可读性分散在不同工具中。 | 查看平台能力 |

## 4. 关键内页模板

### Product Overview

回答“平台做什么、能力如何协同”。依次为：场景总览、四个能力支柱、问题到行动的工作流、支持渠道、权限和审计、CTA。SEO/GEO 是面向市场的入口，其余模块用实际可用状态准确呈现。

### SEO & GEO

访客：增长负责人、SEO 团队、Shopify 商家和代理商。内容顺序：常见问题 → 审计覆盖范围 → 建议和批量处理流程 → 结果验证 → 与 Shopify/Product Knowledge 的关系 → 演示入口。可展示元信息、断链、重定向、结构化数据、内容一致性及索引相关检查，但每项需按产品实际能力确认。**GEO 不承诺特定 AI 助手收录或排名。**

### Product Knowledge

访客：多渠道品牌、内容及商品团队。核心观点：一个可治理的产品事实源，供店铺、官网及搜索内容使用。展示“来源数据 → 事实/属性/关系 → 审核 → 渠道发布或同步 → 差异检测”的流程，并明确事实来源、冲突处理及人工审核机制。

### SiteOps

访客：电商运营、技术负责人及代理商。按“发现异常 → 定位影响 → 给出修复建议 → 验证恢复”组织内容。先聚焦页面可用性、链接、性能与跟踪等确有数据来源的能力；涉及结账、支付、应用健康、Webhook 和订单链路时，需逐项说明可观测范围和所需权限。

### AI Agents

重点展示任务日志与权限模型：监测、分析、建议、审批、执行、验证。提供真实或标注为示意的任务记录，说明哪些操作可自动完成、哪些需审批、如何回滚及如何确认结果。避免“AI 自动修复一切”的承诺。

### Shopify Solution

以“接入 Shopify 后的第一周”说明体验：授权范围、首次扫描、发现问题、审阅建议、跟踪改善。加入适用对象、数据访问范围、常见问题和 CTA。Shopify App 的安装入口仅在应用可安装且流程可用时展示。

### Strapi / Multi-site Solution

以现有多站点实践为基础，展示品牌、站点、语言或市场的层级与内容协作方式。写清与现有 Strapi 的关系、租户隔离、审批及产品事实同步；不要将规划中的多租户能力描述为当前已全面交付。

### Platform / Security / Integrations

How It Works 解释连接、监测、Issue Center、Agent、审批和验证之间的关系。Security 解释授权、数据隔离、最小权限、审计和人工控制。Integrations 按 **Available / In development / Planned** 标记状态；不展示没有明确计划或无法接入的 Logo。Developers/API 页面在接口和文档稳定后开放。

## 5. 内容与转化规范

| 项目 | 建议 |
| --- | --- |
| 主转化 | 企业早期阶段优先 Book a Demo；如已有真实自助接入，再加入 Get Started |
| 次转化 | 查看 Shopify 方案、了解 SEO & GEO、阅读工作原理 |
| 社会证明 | 仅使用获得许可的客户 Logo、可复核的案例和真实数据 |
| 功能状态 | 已上线、内测、开发中、规划中四级内部标记；前台用易懂措辞明确范围 |
| 文案语气 | 具体、可验证，以工作结果和操作流程为中心；避免笼统宣称“全自动”“保证排名” |
| SEO 结构 | 每页唯一主题、清晰 H1、可读 URL、相关内链与页面级元信息；资源页按真实内容持续维护 |
| 语言 | 先确定主要销售市场与官网主语言；英文工作稿需经品牌及销售团队确认 |

## 6. 交付给设计与开发的清单

1. 确认品牌名称、主目标客户、官网主语言与主 CTA。
2. 建立功能清单：已上线、内测、在开发、规划；为每条官网功能声明指定负责人核验。
3. 准备真实产品截图或明确标注的概念图；提供一条可演示的 Issue → 建议 → 审批 → 验证案例。
4. 确认 Shopify 与 Strapi 接入范围、数据权限和可安装/可申请的入口。
5. 完成 Home、SEO & GEO、Shopify、Platform、Security 五页的详细文案与线框，再扩展其他页面。
6. 上线前核对每个 CTA、表单、隐私条款、追踪事件、移动端可读性及结构化数据。

**后续待确认**：平台正式名称；首发市场及语言；可公开的功能边界；Shopify App 状态；是否已有自助试用与定价；可公开客户案例。这些信息决定最终官网文案与导航是否需要收缩。

## 7. 整体规划审视：需要补齐的短板

当前架构覆盖了“我们有什么”，但购买者还缺少“为什么现在买、从哪里开始、多久看到结果”的答案。优先补齐以下六项：

| 优先级 | 短板 | 对官网与产品的具体补充 |
| --- | --- | --- |
| P0 | 首发客户与主场景不够聚焦 | 明确首发 ICP（如拥有一定商品规模的 Shopify 品牌或服务商）、主要痛点和采购者；首页只以一个主场景牵引，再讲平台扩展性。 |
| P0 | 可交付的首个结果不够具体 | 定义接入后 24 小时或首周的真实交付物，例如问题清单、影响页面、修复建议和复检报告；以实际产品能力确定时限。 |
| P0 | 能力边界与路线图容易混淆 | 为每项宣称建立状态、数据来源、所需权限和验证方式；已上线能力主导首页，规划能力进入 Roadmap 或“即将推出”。 |
| P1 | 缺少可证明的差异化 | 建立可复核的演示案例与前后对比，讲清比单一 SEO 审计工具多了哪些工作闭环，避免空泛的 AI 宣称。 |
| P1 | 转化路径不完整 | 分别设计 Shopify 安装/申请、企业预约演示、代理商合作路径；定义线索表单、资格筛选、销售跟进和关键事件。 |
| P1 | 定价和采购风险的信息不足 | 即使价格未公开，也应回答接入时间、授权范围、是否改动主题、数据处理、试用/试点方式、支持服务和退出机制。 |

**建议的阶段推进**：先确立一个 Shopify SEO/GEO + Site Health 的可交付切入点，完成真实的扫描到复检闭环；随后扩展 Product Knowledge 与跨渠道一致性；最后再突出多站点治理和多 Agent 平台能力。官网可以描述整体愿景，但首屏和主 CTA 必须落在当前可兑现的价值上。
